# Reusable Blender sequence execution

Use this for local intermediate 3D frames after choosing the scene and frame range. It does not approve science, appearance, narration or delivery. Assemble audiovisual roughcuts/samples/finals through the existing [phase entry](production-checkpoints.md#start-lock-and-actual-rendering-entry). Existing task-specific launch requirements still apply; the generic runner is not a replacement for a required bounded executor or an unresolved task.

## Prepare one job per shot or coherent scene

Read the [production sequence](engineering-blender.md#bounded-trials-and-reliable-reuse) first. Reuse linked/appended assets and a stable scene driver. Keep shot parameters in JSON rather than generating a new launcher for each revision. Save project-specific files in the project; call [blender_batch.py](../scripts/blender_batch.py) from the unique global Skill.

Start with [blender-job-template.json](../assets/blender-job-template.json). Fill the actual device name, existing Blender executable and driver path; blank entries are deliberately not runnable. Paths resolve relative to the spec file. `inputs` lists all external assets, libraries, fonts, textures, imported project helpers and caches actually read. The runner hashes them, the Blender binary and its own executable script. It executes declared project Python source directly, including imports, so stale `.pyc` files cannot substitute an older driver, helper or resource policy. It checks loaded external images, fonts and libraries again after frame-state changes; native sequence textures in evaluated nodes use Blender's actual frame mapping, and UDIM images bind each tile. Declare every sequence frame the job uses, not just its first image. Custom file reads, simulation caches and external services still require explicit dependency declarations/checks; this is not a universal dependency crawler.

    python <global-skill>/scripts/blender_batch.py prepare shot-spec.json shot-job-v1.json
    python <global-skill>/scripts/blender_batch.py run shot-job-v1.json --blender <existing-blender-executable>
    python <global-skill>/scripts/blender_batch.py run shot-job-v1.json --blender <existing-blender-executable> --resume

`prepare` writes a new immutable job, including its output directory, dependency hashes and executor hash. Changes to scene, assets, settings or executor require a new job/output version; do not edit the signature. No complete Skill copy is made in the project. Continue an existing job with the same version only when its inputs remain valid. Global updates require explicit migration; do not hot-switch a running batch or rewrite old receipts.

`frames` is a sorted integer list or inclusive comma-separated ranges such as `1:100,151:200`. These are native Blender frame numbers, not zero-based video indices. `motion_preview` requires consecutive frames at the declared output fps; sparse `lookdev` images do not prove smoothness. `--frames 1:25` selects a subset of the frozen job, and `--resume` can then complete the remaining frames. A patch keeps its intentional gaps; never fill those gaps by interpolation or by guessing adjacent source frames.

## Scene adapter

Choose exactly one source:

- `blend`: an existing baked/keyframed scene whose animation is reproduced by `scene.frame_set(frame)`. Check at least two different times before treating a saved file as render-ready. A scene saved from a procedural Python state is not automatically a baked animation.
- `driver`: a Python module with `build(spec) -> bpy.types.Scene` and `set_frame(scene, frame, spec) -> JSON-serializable metadata`. Build/import geometry once per process. Update transforms, visibility, materials or animation state per frame. The driver receives `spec.params`; it does not launch Blender, write frame receipts, choose a fallback device or render frames itself.

An adapter for an existing `build_once()` / `set_state(index)` project should call those functions and document its native-frame-to-index mapping. Declare the imported helpers in `inputs`; reuse their geometry rather than rebuilding a second version. Keep exactly reproducible state for out-of-order patch frames. Bake simulations/caches when their result depends on prior playback; arbitrary random-access evaluation is not valid for an unbaked simulation.

Keep ordinary synchronized narration/accessibility captions as a separate editable 2D layer. Only necessary single-letter markers are allowed in 3D picture; words, abbreviations, numeric/unit labels and explanation plaques are prohibited even as 3D text. Use actual editable scene letter geometry under the [single-letter spatial rule](spatial-typography.md); a separate collection/view layer is allowed, with the same camera, depth/holdouts, occlusion and relevant lighting. `set_frame` can return anchor metadata for compositing or diagnostics: frame/time, stable object/anchor ID, pixel coordinates, depth and visibility. Derive coordinates from evaluated world transforms and the actual camera, e.g. `bpy_extras.object_utils.world_to_camera_view(scene, camera, world_point)`; test bounds, positive depth and occlusion separately. Projection alone does not establish visibility or turn a screen glyph into spatial text. Keep arrowhead/stem geometry editable and preserve its existing semantic/construction requirements.

Formal frames and quality samples use this film's `design.output.width/height` under [HD output](quality-acceptance.md#hd-video-output), verified at 100% in actual rendering and preserved in compositing/encoding. The `blender-job-template.json` 960×540 is only an internal `motion_preview` starting point, not a formal sample/final preset. Formal jobs explicitly override dimensions/fps and choose sampling by actual risk, not technical-preview parameters as final quality standards.

## Hand off raw frames to the edit

Keep the accepted narration and editable text/annotation source separate from the raw sequence. The edit records each source job/signature, verified frame files, source fps, selected native range and its destination timeline interval. A sparse patch replaces those exact frame numbers in the original sequence; it is not a shorter consecutive clip. Check the completed range for missing/duplicate frames before encoding at its recorded fps. Do not stretch picture or cut voice with `-shortest` merely to hide a duration mismatch.

Use the existing editor or FFmpeg adapter to combine scene picture, matching 3D text passes, delivery-size 2D captions, narration and sound. Preserve linear/color-transform handling for EXR rather than treating it as display-ready PNG. A 2D caption correction can reuse verified picture; a 3D text correction rerenders the affected text geometry/material pass and any changed receiving shadows/reflections or occlusion dependencies, reusing unaffected beauty frames. A voice edit reuses picture when timing still matches. New timing, camera, geometry or visibility can change dependent ranges. Verify the recomposed result and applicable audiovisual scope through the existing phase entry; frame reuse is not automatic review reuse.

### Optionally reuse light groups instead of rerendering every adjustment

When repeated key/fill balancing is genuinely needed and the project already has usable Light Groups/separate lighting passes, rebalance gains locally in compositing, preserving linear masters, channel mapping, actual output files/hashes and editable composition. Reuse only real passes verified in this environment. Generic PNG/OPEN_EXR frame support does not establish multilayer EXR/Light Groups; do not invent JSON render keys. Authors configure new passes in supported scene/compositing workflows when needed, checking actual output/reuse benefit in existing representative work rather than adding a per-episode pass-test gate.

Changed source position/size, shadows, occlusion, geometry, materials or explained phenomena still require affected rerenders. Ordinary grading/2D brightening cannot create missing real reflections/shadows. Without required passes, use the current available workflow without automatically changing engine, installing tools or calling cloud services. Author-declared extra pass deliveries still require version/scope checks; tool completion is not quality approval.

## Explicit color settings and actual readback

The generic runner accepts only its documented `render` keys; an unsupported key is an error, not an applied setting. Optional `render.color_management` accepts `display_device`, `view_transform`, `look`, `exposure` and `gamma`; use enum names supported by the actual Blender/OCIO configuration. Absent keys inherit the authored scene. Explicit values are applied in order and read back; invalid/clamped/mismatched values fail before rendering. Do not put a flat `render.exposure` or invented material/light parameter in the spec and assume it works. Other scene, material, texture, light and output controls belong in the declared driver/baked scene. The receipt records actual color state plus available sampling, denoising and light-path diagnostic settings; it does not certify appearance.

For [grain, shimmer and compression diagnosis](art-direction.md#image-cleanliness-locate-the-source-of-snow-like-noise-first), compare the local raw output and affected post-processing stages before changing quality. The `motion_preview` template is a technical preview, not a final-look preset. No universal sample/exposure/brightness pass line is implied. Existing frozen jobs keep their input/signature history; a changed executor or settings requires an explicit new job/migration rather than editing its old receipt.

## Complete a repair cycle before expanding

For video repairs, give one author the complete affected interval and its entry/exit joins. In the existing assignment/work log, fix the observed defect, expected visible change, last playable version and next playable deliverable before editing. A corrected still or a new job name is not a completed repair.

- **Test the mechanism, then batch diagnostics.** For cutaway/visibility/camera faults, use the real driver to check evaluated transforms, cutter coverage, visibility events and camera clearance throughout opening, hold, closing and joins. Fix shared state/geometry before polishing isolated frames. Send all known risk states in one coherent request; reuse the scene build and unchanged media. Numerical checks locate risk; they do not approve appearance.
- **Bound the diagnostic work.** The parent sets a task-specific sparse-batch allowance from the known questions and measured costs; there is no universal render count or minute limit. Bind new/continued Blender video-repair diagnostics to `repair_scope` below. Renaming jobs, changing source/output versions or subdividing `--frames` does not create a new allowance. Genuine standalone asset work keeps its existing scope; intermediate video work cannot be relabelled as asset-only to evade this rule.
- **Stop the loop, resolve the cause.** When the allowance is exhausted, a forecast is missed, or the same defect family returns without usable continuous progress, stop new isolated diagnostics. Return the current implementation, actual findings/costs and bottleneck to the parent in one packet. The parent chooses a bounded cause-level change and continuous deliverable; it must not merely forward another frame request or silently replenish the allowance. Preserve the requested effect and quality: stable topology, adequate cutter coverage or deterministic cached states can replace a fragile implementation without dropping the animation.
- **Produce the continuous candidate.** Render the complete changed native interval and joins at the declared fps, using suitable low-cost spatial/shading settings for internal motion review, then check final-engine-specific risks in the intended engine. Once that sequence exists, assemble it promptly into a playable candidate with retained matching voice/text through the applicable edit/phase entry. Do not schedule another cosmetic lookdev round first. A complete raw sequence is not yet that playable deliverable; known defects remain failed/unreviewed, and neither proxy quality nor elapsed time authorizes G3/G5.
- **Review once per useful version.** Review the complete changed cycle and joins together, return one prioritized defect packet, and recheck the affected scope after repair. Sparse stills answer static questions; they never establish motion fixed. Reuse current observations rather than rediscovering each endpoint in separate reviewer calls. Independent required review remains independent.

Use existing task messages and receipts for the next output/estimate, cumulative wall time, measured build/render/edit costs and latest playable file. Keep uninstrumented gaps unknown; do not count a new spec, preflight report, still set or promise to assemble as playable progress. Required job/feedback records stay current, without rebuilding unchanged episode paperwork. Continue unrelated authorized work while a dependency is repaired.

### Task-bound diagnostic admission

For Blender video-repair diagnostics, add `"repair_scope": "<existing private scope JSON>"` to the job spec before `prepare`. This optional runner field preserves compatibility for other raw-asset jobs; using it for video repairs is mandatory here. The scope JSON has:

| Key | Value |
| --- | --- |
| `schema_version`, `task_id` | `1`, a stable simple task ID for this repair decision |
| `issue` | The actual defect and expected visible change |
| `output_root` | One private task directory, relative to this JSON or absolute; every versioned output is below it |
| `frames`, `fps`, optional `fps_base` | The complete consecutive native interval including required joins, and its actual frame rate |
| `max_diagnostic_batches` | A required integer >= 0 chosen for this task, with no global default |

The scope is frozen as an input and bound once at that root. Before scene build, the runner locks task admission and counts charged selections in existing attempt receipts across all output versions. Actual selected frames determine diagnostics, including sparse `--frames` on a nominally full job. Failed builds after admission retain their charge; resource refusal before admission and verified no-work reuse do not consume it. Matching frozen-job resumes of the same/subset selection reuse a charge; expanding that sparse selection consumes another. A complete interval request can proceed to finish the cycle and never replenishes the diagnostic allowance. Refused attempts are retained.

The parent cannot edit the bound scope, delete history, use a fresh root per revision or invoke Blender directly to bypass refusal. A genuinely new bounded decision preserves its predecessor and reason in the existing work log; it is not an automatic reset or new approval ceremony. On an ongoing task, inspect past diagnostics first and choose the remaining allowance accordingly (including zero when spent); historical jobs/receipts are not rewritten or automatically counted as newly guarded attempts. Explicitly migrate changed executor/input bindings; never hot-switch a running job.

This guard limits new partial render attempts in the declared repair scope. It does not prove useful visual improvement, enforce playable assembly, approve quality or sandbox arbitrary shell commands. The parent/producer must enforce the continuous-deliverable handoff above; a full sequence or a new scope alone cannot establish progress or acceptance.

## Device, ownership and recovery

Cycles jobs explicitly select `CPU` or `GPU`; GPU jobs select the actual backend and exact enumerated device name, with `device_id` when names are ambiguous. No implicit CPU fallback or utilization ceiling is implemented. Keep applicable host/user limits and existing project queue, ownership, capacity and budget checks. An optional `resource_check` Python file can expose `check(spec) -> {"ok": bool, ...raw observations/reason...}` to reuse an existing check immediately before building. Include that module and its dependencies in `inputs`. A false result is recorded and stops execution; the hook cannot invent its own policy threshold. Consult the [current-evidence rule](production-checkpoints.md#conditional-reuse-of-static-evidence-and-fresh-dynamic-checks).

The Blender process holds an OS lock for its output job. If its launcher disconnects, the worker still owns the lock. Do not delete the lock file to force a retry. Inspect the actual process and `state.json`; a failed or interrupted job can resume only once the lock is available and input hashes match. An existing output directory without the matching `job.json` is never adopted.

Each frame has a hash, source-job signature, actual settings, optional anchor metadata and measured state/render-write times. Resume reuses only matching files/receipts; incomplete or corrupt job-owned files are preserved under `invalid/` before replacement. Completed attempts remain in `attempts/`. If source changes during execution, the attempt is marked `inputs_changed`; restored source bytes do not retroactively validate those frames. Keep that output and prepare a fresh job. Completion is always `complete_unreviewed`, not a quality pass.

## Integrity validation without repeated visual review

Separate automatic file integrity from visual review: actually validate new-frame contents/target dimensions; corrupt/changed frames cannot be reused. Reuse decode results only when content SHA, job/render and validator identity match, rechecking content hashes across calls rather than trusting existence, size or mtime. Do not repeatedly decode the same validated content or call cache/`complete_unreviewed` a visual pass. Completion statistics still cover the entire job; a selected subset cannot establish whole-job completion.

Combine a scene's continuous frames/known risk states into one meaningful execution request rather than repeated single-frame launches, retaining real locks, input-change checks and failure history. Full-job content scans may still cause I/O; do not claim caching removes every scan or proves production speedup. Record validation/hash/decode separately from state-update/render-write times, including resume startup scans; demonstrate optimization at equal quality.

After normal-speed viewing, locate issues and complete repair cycles through [risk-based rechecks](quality-acceptance.md#risk-based-rechecks-and-evidence-reuse), without sending every sequence frame to a model. Full final-encode decoding checks a different output and cannot be replaced by raw-frame passes. Do not repeat the same terminal check for multiple table fields within one responsibility.

## Rendering cost and scheduling

Apply the shared [local execution, minimal transfer and throughput policy](tool-routing.md#local-execution-minimal-transfer-and-throughput) to working data, devices, concurrency and output review. Keep raw image sequences local; send only the evidence or changed assets actually needed by a remote step.

Use target-fps motion previews with inexpensive viewport/Workbench, EEVEE or low-cost Cycles settings suited to the actual scene. Validate engine-specific transparency, reflections, cutaways and fine fibers in the final engine before expanding. Keep the approved look, geometry and temporal continuity; do not lower samples blindly or hide defects with denoising. Persistent Data is enabled by default for Cycles but can be disabled for a demonstrated memory constraint. GPU setup and scene building occur once per worker.

Separate resource checks, scene building, frame-state updates and render/write time using attempt receipts. Record editing, reviews, queueing and packaging separately in the existing work log. These timings do not include all Blender startup or human/agent iteration time. Estimate remaining cost from representative measured frames and identify the scene/profile; do not claim a universal speedup from one warm-cache batch. For a before/after comparison, hold the scene, frame range, resolution, engine, device and quality settings constant; record startup/warm-cache conditions and compare decoded frame output as well as wall time. A synthetic startup/build-reuse test proves only that mechanism, not the speedup of an existing production that already builds once.

Flamenco is an optional scheduler, not a new production gate or a prerequisite for a single machine. Prefer the existing local execution path; add remote workers only for an authorized need or a measured benefit after transfer, synchronization and queue costs. Its [built-in Blender sequence job](https://flamenco.blender.org/usage/job-types/builtin/) accepts frame ranges/chunks and image output; use it directly for a verified baked `.blend`. For procedural scenes, a custom task must invoke the same global runner and declared driver. Preserve logs, job identity and final input/frame checks. The local runner serializes one output job; distribute independent shot jobs rather than concurrently writing the same directory. Multi-machine deployment additionally needs verified shared paths and storage-lock behavior; local tests do not establish distributed safety. Do not install services, copy the Skill into projects or reset existing tasks merely to adopt this workflow.

Borrow their separation of assets, shots, previews and edit; adopt extra infrastructure only when it solves a measured production need.
