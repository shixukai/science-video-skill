## Local execution, minimal transfer and throughput

Bandwidth conservation applies to the parent and every subagent. For local routes, run capable preparation, processing and validation locally. For Google Flow, generate picture and physical foley in Flow; use the [commissioned narration and scoped mastering/compositing workflow](google-flow-production.md#build-a-cloud-generated-narration-master-for-each-language), not local substitutes or a missing-output bypass. Reuse working assets and downloads and send only the references needed for the selected operation.

- **Keep processing near the data.** Reuse the installed tools, confirmed model locations, loaded models and verified assets. Run file searches, JSON/log filtering, hashes, measurements and report generation locally; return paths/IDs, concise results and relevant errors. Keep full logs, source media, weights and intermediate frame sequences locally instead of repeatedly sending them through the conversation or a remote runner.
- **Transfer only what the next step needs.** Use local review when the reviewer has actual access and perception capability; remote media calls must satisfy the [pre-submission requirement](#review-media-without-repeated-uploads). Remote processing needs an explicitly selected service or a demonstrated local capability/capacity gap; convenience or faster remote execution alone cannot override bandwidth conservation. Reuse verified local models/assets and cached downloads; do not fetch or upload a whole project/library for a local change. Use existing authorization without adding a per-transfer permission request.
- **Reuse local working data.** Prefer an appropriate local fast disk for new active working sets and temporary media. Fetch missing assets from the approved library/NAS on demand, reuse verified local copies and archive changed files incrementally. Preserve originals, existing job-bound paths, version evidence and required backups; do not move a running job's inputs or repeatedly copy a whole library/project for a local change. Cache/reuse remains subject to the existing input-integrity checks.
- **Use CPU and GPU actively; preserve quality.** Select compatible GPU rendering/inference and hardware decode/encode when they meet the required quality. Overlap independent CPU preparation, analysis and post-processing with GPU work. Do not pre-emptively simplify materials, lighting, geometry or output quality because rendering might be expensive. Verify the actual selected backend and per-stage time; investigate idle gaps and inherited CPU/fixed-thread settings before treating low GPU utilization as a hardware limit.
- **Scale useful parallelism.** Coordinate worker count, threads per worker and batch size using current memory/VRAM demand, actual throughput and errors. Sustained high CPU/GPU usage is acceptable while the system remains responsive and stable. Increase useful concurrency when capacity remains; reuse a valid measured setup and put necessary calibration in the existing short sample, not a benchmark before every launch. The target is qualified output per unit time, not a utilization percentage.
- **Back off before system responsiveness is lost.** Use available current observations of memory/VRAM pressure, sustained paging or I/O stalls, desktop responsiveness and device/thermal errors. When resource contention causes slowdown or instability, reduce this task's workers, per-worker threads or batch size, or pause new submissions; preserve completed frames and resume at a demonstrated stable setting. Handle OOM/device faults in the affected job instead of repeatedly relaunching the same failing workload. Keep normal hardware/OS protections, job ownership, output locks and explicit host/user/task-specific limits; do not terminate unrelated tasks. Missing optional telemetry is not a new blocker. Resource admission follows the [current-evidence rule](production-checkpoints.md#conditional-reuse-of-static-evidence-and-fresh-dynamic-checks), without invented utilization caps, fixed reserve quotas or idle-wait gates.
- **Optimize the complete workflow.** Reuse initialized processes/scenes, batch compatible work, overlap independent stages and resume valid outputs. Re-render only affected ranges; text/audio-only changes normally recompose existing frames. Compare end-to-end time and qualified output throughput at the same quality, including transfer, loading and I/O. Keep the accepted resolution, motion sampling, geometry, voice and review requirements; high utilization alone is not proof of improvement. Use the existing [timing records](production-checkpoints.md#segmented-timing-and-controlled-service-reuse) for measured configurations and results.

## Review media without repeated uploads

**User review materials use clickable file links.** When asking the user to judge a video, audio file, image, document or report, verify that the current intended file exists and return a normal Markdown file link with a short material/version label and an absolute filesystem target. Use forward slashes in Windows link targets and angle brackets around targets containing spaces. Do not wrap the whole link in backticks or use file://, vscode:// or an invented web URL. A bare path or inline-code path alone is insufficient for the requested handoff. For several requested candidates, give a clearly labelled link for each and briefly identify the relevant review question or interval.

Use the verified local or [designated NAS](production-checkpoints.md#move-accepted-and-published-videos) file. Keep media at its authorized location when preparing a link. Return links without attaching/uploading media, embedding players/images/media tags, invoking preview/display tools or opening a player automatically. Do not substitute GIFs, thumbnails or frame galleries for the same review material in chat. The user may click the link to open it intentionally; this is distinct from automatic presentation. A later explicit user request controls any change to this handoff. Agent inspection remains subject to the media-transfer requirements below.

**Mandatory before each outbound media call or batch:** establish the specific production, review or delivery need and the recipient's required capability, check prior submissions for the same content/context, and select the smallest sufficient representation and range. Record purpose, recipient, selected files/ranges/hashes and their locally measured byte total in the existing work/review log; one batch entry is enough. If necessity, deduplication or sufficient payload selection is unresolved, do not submit media: prepare/check locally or retain the corresponding review as unreviewed while continuing independent work. Measure local files before sending them. For tools that create media during the call, bound the requested dimensions/range/count before calling and record returned sizes when exposed; unknown sizes remain unknown. Do not invent a universal MB/frame cap or claim file sizes are wire measurements.

Quality, full-film coverage and independent review must be achieved within this constraint, not used as blanket exceptions for raw-frame uploads or repeat batches. When a proxy loses needed detail, send only the necessary higher-fidelity range or contextual detail. Only an explicit user instruction changes the scope of this constraint. Apply the user's current allowance as well as restrictions: permission for moderate review uploads permits context-preserving contact sheets, necessary original detail or short playable intervals for a capable recipient. Do not keep enforcing an older self-chosen byte ceiling or shrink to a contextless crop. Reuse one concise existing log entry for the review bundle, appending actual files/results rather than creating per-frame approvals; already authorized transfers need no repeated user permission. This does not authorize whole-project uploads, routine full-frame-sequence image calls or automatic media display in chat. On continuation or a new user transfer restriction, apply the current rule before the next media submission; this requires no render restart or rewriting of historical receipts.

Local files do not imply local perception. Treat `view_image`, `emitImage` and image-bearing tool results sent to a remote model as media submissions. Local decoding, hashes, geometry checks and FFmpeg measurements can stay on the computer. A path or a successful playback command does not give an agent video/audio perception.

1. **Detect and select locally.** Run applicable frame-integrity, black/freeze/change, geometry/camera and audio checks locally; return compact findings and time ranges. These checks locate candidates for inspection, not aesthetic or scientific approval. Keep the original frames and full logs on disk. Do not loop image-view tools over a whole frame sequence as routine review, or send every intermediate render merely because it exists.
2. **Choose media for the question.** For motion and pacing, use a locally encoded, normal-frame-rate clip with the required sound and complete affected cycle/joins when the reviewer can actually perceive it. For static diagnosis, start with selected key states or a readable, labelled contact sheet, then request originals or contextual crops only where detail is unresolved. Preserve source identity, frame/time, crop and scale. Do not paginate the entire sequence into sheets to imitate playback. If continuous perception is unavailable, mark that coverage unreviewed; hundreds of still-image calls cannot supply it. Keep the existing normal-speed first-view and independent-context rules.
3. **Match the representation to the review.** Prepare lightweight review derivatives locally; do not change production masters. Use resolution/compression adequate for the actual question. Full-resolution text, fine geometry, texture, color or compression defects may need original frames and surrounding context. Proxy findings apply only to what remains observable; they do not replace required final-encode or full-film review. Choose a bounded batch for the current question rather than a universal frame/byte quota.
4. **Avoid duplicate submissions.** Assign one owner per review responsibility, media version and range; retain the separate G5 explanation and expression reviewers. Update the pre-submission entry with the actual result status and any changed crop/scale. Reuse observations for unchanged content in the same context; the parent receives paths, time-coded findings and only needed evidence, not another copy of every inspected frame. Repeat a submission only for a concrete reason such as missing detail, a new comparison or required independent review. A fresh reviewer must receive the media it needs without relying on the author's verdict; a shared path/hash is not a shared model cache. If a batch response is missing or oversized, inspect its status and resend only the missing needed items, not the whole batch automatically.
5. **Account honestly.** When diagnosing transfer cost, count actual media-submission events and repetitions, and record locally measured derivative sizes in the existing log. File bytes are an estimate of selected payload, not measured network traffic: encoding, resizing, cache behavior, retries and protocol overhead may differ. Report wire bytes only when actually measured and scoped. Do not upload more images to investigate an upload problem or print base64/full media logs into the conversation.

### Blender-to-ComfyUI pipeline trials

Use a short paired trial when a neural redraw is a plausible improvement for the selected shot. It is optional, not a prerequisite for ordinary Blender production. Keep the [selected production route](#lock-the-primary-tool-by-final-film-style); a trial does not make generated pixels equivalent to controlled geometry.

1. **Freeze a shared shot.** Use the same Blender scene, camera, objects, action, native frame range and viewing conditions. Define visible invariants such as component count, holes, interfaces, contact order and final state before rendering. Save the beauty sequence and the actual control input. Choose a frame count and resolution supported by the candidate model; keep both comparison clips at the same duration and fps. Identify native versus resized/interpolated outputs and any differing settings. This compares complete pipelines, not necessarily one isolated variable.
2. **Verify the actual control path.** Inspect the running node schema and saved graph: the full condition sequence must reach the video-control input, with the reference frame connected separately when used. First-frame I2V alone is not a controlled video-redraw test. A native-node example is `LoadVideo → GetVideoComponents.images → Canny → Wan22FunControlToVideo.control_video`, with the beauty first frame connected to `ref_image`, matched high/low-noise sampling, then VAE decode and encoding. Consult the [upstream template](https://github.com/Comfy-Org/workflow_templates/blob/main/templates/video_wan2_2_14B_fun_control.json), verifying the installed schema and model/accelerator pairing. Record actual versions, hashes, graph, seed, sampling, condition parameters and frame mapping. Depth, Mist, Normal and Canny are not interchangeable.
3. **Check preservation before appearance.** Inspect the encoded output for the required objects, openings, thin layers, motion and relationships; attractive texture cannot offset a lost part or changed mechanism. Record concrete defects by frame/time. Review continuous stability through the existing [actual viewing requirements](quality-acceptance.md#reviewers-and-viewing-safety); stills can establish local defects but cannot prove smoothness or absence of flicker. Preserve a failing candidate and its repair cost. Full-frame neural output remains `ai_generated`; for masked redraw or compositing, record generated and retained controlled layers separately, with their actual Blender/control dependencies. Use controlled geometry for an explanation whose required relationships the redraw does not preserve.
4. **Measure time to a usable result.** Follow the existing [stage timing definitions](production-checkpoints.md#segmented-timing-and-controlled-service-reuse). Report shared preparation once and each route's preparation/control export, startup, queue, loading, execution, encoding, repairs and actual review. The redraw route includes its required Blender work: if controls come from a beauty render, include that dependency; a cheap depth/clay-export alternative is a different trial. Separate first deployment/download costs from reusable work and state cache conditions. Measure route wall time; overlapping stages are not additive. Mark untimed work and unseparated stages instead of calling execution time the full total or pure inference.
5. **Adopt the demonstrated use, not the tool name.** A useful production method needs the required quality plus an observed quality or total-time benefit at comparable viewing conditions. A failed redraw still informs shot selection; it does not establish that all models fail. Keep unreviewed results as candidates. One short trial does not justify a series-wide engine/model change, universal speed claim, fixed low-VRAM setting, or replacing material/light work with automatic redraw.

Recheck tool/asset changes by [affected dependencies](quality-acceptance.md#handling-failures); continuations compare [global migration](global-skill-installation.md) without hot-switching active jobs.

## vork execution

The agent automatically decides whether to use `vork` (`voyager-so/vork`, `source_id: "vork-engine"`)—without asking the user to choose an engine unless the user explicitly specifies one—by evaluating mechanism fit and local GPU capability:
- **Use `vork` (full 3D episode, specific 3D shots, or supporting passes in realistic/Blender episodes)** when the visual payoff centers on invisible physical fields, electromagnetic/acoustic waves, standing-wave nodes and antinode lobes, thermal/concentration gradients, Slang GPU compute simulations (particles, fluids, swarms, field lines), custom optical/procedural/wireframe-reveal shaders, tracked-camera 3D relighting over authorized plates, or clean code-authored parametric/`glTF` studio mechanisms with transform/quaternion/material animation.
- **Prefer `Blender` instead of `vork`** when the work requires complex multi-part mechanical CAD/mesh modeling, animated boolean/modifier cutaways, non-rigid mesh deformations, armatures, character rigging/mocap/lip-sync, cloth/soft-body/rigid-body constraint solvers, `.blend`-native shared-library rigs, or when the current host lacks a compatible hardware-ray-query GPU. On the local realistic route, keep final multi-shot assembly, narration and captions in MoneyPrinterTurbo.

1. **Local GPU runtime and setup:** Execute locally on a compatible hardware-ray-query GPU (Vulkan on NVIDIA RTX or Metal on Apple Silicon; Windows default `%LOCALAPPDATA%\Programs\vork\vork.exe`, Unix `~/.local/bin/vork`). Check `vork --version` and run `vork setup` once per build/driver to warm shader caches and verify ray queries, GPU OIDN denoising and FFmpeg `h264_nvenc`/`libx264`. Set `VORK_NO_UPDATE_NOTIFIER=1` during automated jobs. Do not send scenes or assets to `vork cloud` without explicit user cloud authorization.
2. **Scene schema, OpenPBR and animation tracks (`version: 2`):** Query exact fields on demand with `vork help`, `vork help animation --all`, `vork help programs --all` and `vork help field <PATH>` instead of guessing parameter names:
   - `std/openpbr` inputs use OpenPBR names (`base_color`, `base_metalness`, `specular_roughness`, `coat_weight`, `emission_color`, `emission_luminance`); glTF/Principled `metallic` fails validation.
   - `scene.animation` track `path` arrays contain string segments only (for example `["nodes", "<name>", "translation"]` and `["nodes", "<name>", "rotation"]` with `[x, y, z, w]` quaternions or node-matching Euler angles; reference animated material parameters through top-level named `materials` rather than integer array indices). Literal `[x, y, z]` camera `target` is structural; point `target` at a named node and animate that node's `translation` when camera aim moves.
   - Frame ranges include both endpoints (`--frame-start 0 --frame-end N-1` renders `N` frames at `render.fps` × `render.duration`). Pre-roll simulations and camera tracks so frame 0 is already moving when used in openings or active cuts.
3. **Profiles, HD quality and episode records:** Match `render.resolution` to episode `design.output` (default `1920x1080`). Iterate layout/blocking with `--profile std/previs` or `std/draft`, then render deliverables with `--profile std/final` (8 samples + OIDN) or `--profile std/path` when hybrid `std/final` darkens interior indirect/glossy bounces; raise `--set samples=32` (or higher) when 4/8-sample OIDN softens fine geometry edges, mottles surfaces, roughens defocus or alters sparse highlights. ## Colab CLI and remote GPU integration

Google Colab GPU runtimes are the **default (`colab_first`)** compute target for **3D Blender Cycles rendering** (samples, continuous sequences and finals via `scripts/colab_cli.py blender-render`) and heavy ComfyUI inference (`Wan2.2 I2V-A14B FP16`, `Wan2.2 Fun-Control A14B BF16`, `LTX-2.3 22B BF16`, `HunyuanVideo 1.5 720p+1080p SR FP16`, `SeedVR2 7B Sharp FP16`, `ACE-Step 1.5`) whenever Colab authorization and live preflight pass, with automatic fallback to local GPU workers. Installing or reading this Skill grants no cloud spend or Colab compute-unit authorization. Keep scene authoring, quick local packing/single-frame checks, orchestration, local narration (`IndexTTS-2.5` / `edge-tts`), Google Flow browser automation, human audiovisual review, NAS archiving and platform publishing local, and enforce the same `license_tier` commercial-safe gate on Colab and local workers.

### Choose between two authorized access modes and fall back locally

1. **Mode A (Default) — `google-colab-cli` (`colab`, `source_id: "google-colab-cli"`, Apache-2.0):** **Default Colab access and execution mode** whenever authorized and verified on the current host (native Windows/Linux/macOS or WSL2). Always run `python -X utf8 scripts/colab_cli.py preflight --check-auth` first; when ready, use `scripts/colab_cli.py` (`blender-render`, `run-ephemeral`, `sessions`, `usage`, `stop`) or non-interactive `colab` subcommands for scriptable GPU provisioning, direct packed-`.blend` strided multi-shard Blender Cycles batch renders, and CLI-managed worker lifecycle without browser copy-paste or Cloudflare tunnel limits.
2. **Mode B (Secondary Fallback) — Browser notebook + authenticated HTTPS tunnel (`colab_node.py connect`):** Use only as a fallback when `colab` CLI is unavailable/unauthenticated on the host, or when an already-mounted human Google Drive persistent model cache (`/content/drive/...`) is actively serving a long-running ComfyUI worker. Require authenticated HTTPS (`Authorization: Bearer <token>`); never expose unauthenticated public ComfyUI ports or commit tunnel URLs, tokens or session files.
3. **Automatic local fallback:** Whenever Colab is unauthorized, unconfigured, offline, unauthenticated, quota-rejected (`HTTP 400`/`412`) or lacks the requested model/custom node/host platform support, fall back automatically to the local fast-disk ComfyUI worker (`:8191` / `:8190`) or local Blender GPU. ### Default Colab 3D modeling and visual style (high-poly industrial)

When authoring and rendering 3D science explainers on Colab Cycles GPU without a conflicting explicit user style override, follow the normative **[High-poly industrial modeling standard for Colab 3D](engineering-blender.md#high-poly-industrial-modeling-standard-for-colab-3d)** (`high_poly_industrial_3d`, modeling profile `high_poly_industrial_v1` — precision CNC/CAD hardware and mechanical teardown fidelity across whole assemblies, cutaways, exploded views, macro mechanism close-ups and grounded industrial workbenches):

- **High-poly CAD & CNC hard-surface geometry (zero low-poly faceting):** Build hero curved parts at `>= 64` radial segments (`96–128` for macro hero rings/bezels/glass cylinders; `>= 32–48` for secondary visible fasteners/pipes), combine open-licensed high-poly CAD/glTF (`CC0`/`CC-BY`) with multi-part procedural CNC/lathe assemblies, real physical chamfers/angle-limited `Bevel` (`0.15–0.8 mm` machined / `1–3 mm` cast/molded, `segments >= 3`), `WeightedNormal`/`EdgeSplit` flat-face control, real wall thickness, `0.15–0.5 mm` panel shadow gaps, applied uniform `(1, 1, 1)` scales, and authentic mechanical fasteners/knurling/fittings. Ban bare primitive blocks, flat-shaded curved meshes, single-sided cutaway planes and chunky textbook arrows.
- **Role-separated neural 3D (`TRELLIS.2` / `Hunyuan3D 2.1`):** Restrict single-image neural 3D meshes (`TRELLIS.2 --geometry-only` MIT shaded in Blender, or `Hunyuan3D 2.1`) strictly to **organic, crinkled, soft, porous or matte sculpted props**. Never use marching-cubes neural SDF meshes for glossy CNC machined metals, optical glass or precision mechanical parts.
- **Industrial PBR finishes, studio lighting & true optical physics:** Pair distinct machined metal/anodized/cast/polymer/rubber finishes under broad studio softboxes + negative-fill flags on grounded graphite/matte industrial benches; render glass/fluid enclosures with physical wall thickness, bevels, `IOR`, `visible_transmission = False` on bright area backlight strips (zero glare bars), clean cutaway cap finishes, and `<= 1 mm` micro-optic force cues.
- **Deterministic baked Blender physics for strided Colab shards:** Drive physical beats with real Blender simulations (`Bullet` rigid bodies, cloth, fluid/particle physics), then bake evaluated transforms into headless-safe **quaternion F-curves** (`evaluated_depsgraph_get()` -> `location` + `rotation_quaternion` keyframes, then remove `rigidbody_world`) and pack all textures (`pack_all()`) before uploading so strided multi-shard renders (`--shards N`) match identically with zero cache divergence.
- **Local modeling audit + full-resolution `1920x1080` hero preflight before cloud dispatch:** Run `python -X utf8 scripts/colab_cli.py audit-blend --blend <scene.blend> --shards <N>` locally and inspect full-resolution `1920x1080` hero stills across every beat (hook, cutaway, physics peak, continuity return) before dispatching via `scripts/colab_cli.py blender-render` (which uses `--adaptive-threshold 0.015` and OIDN `RGB_ALBEDO_NORMAL` by default to keep machined bevels and micro-details crisp, and records `industrial_modeling_audit` telemetry in the receipt).

### Platform preflight, authentication and non-interactive agent boundaries

- **Verify host readiness first:** Upstream `google-colab-cli` `README.md` currently declares **Linux and macOS** support (`colab update --install` is Linux/macOS-only), while its package is pure Python `>=3.12` with cross-platform `filelock` and OpenSSH support. Before routing through `colab` CLI—especially on Windows—run read-only preflight:

```sh
python -X utf8 scripts/colab_cli.py preflight --check-auth
```

  If native `colab` is absent on Windows, `scripts/colab_cli.py` automatically probes WSL2 (`--transport auto|native|wsl`, optional `--wsl-distro`); if unavailable or unauthenticated (exit 1), route to Mode B or local GPU without blocking production.
- **CLI authentication (`--auth {oauth2,adc}`):** Global flags go *before* the subcommand (`colab --auth=adc sessions`). For headless/agent automation, prefer `--auth=adc` after a one-time human login with all four required scopes (`gcloud auth application-default login --scopes=openid,https://www.googleapis.com/auth/cloud-platform,https://www.googleapis.com/auth/userinfo.email,https://www.googleapis.com/auth/colaboratory`). Default `oauth2` uses a human copy-paste consent flow cached in the OS native keyring (`keyring`). Diagnose 401/403 immediately with read-only `colab sessions` or `colab whoami`. Never confuse `colab auth` (which injects VM-side GCP credentials for BigQuery/GCS) with CLI authentication.
- **Non-TTY safety & session isolation:** Never invoke interactive `colab repl`, bare `colab ssh` (without `-- CMD`), `colab auth`, or `colab drivemount` from a non-interactive agent—they expect a human TTY and will hang or allocate an unwanted VM. If a CLI-provisioned VM requires human Drive mounting (`colab drivemount -s <name>`) or browser inspection, print `colab url -s <name>` so the user attaches to that *same* VM rather than allocating a second runtime. Isolate concurrent or agent-owned session metadata via global `--config <private-scratch-sessions.json>` (0600 permissions; keep outside this Skill and committed repositories).

### Provisioning, execution, bandwidth discipline and mandatory teardown

- **Explicit session naming & validated GPUs:** Always pass `-s <name>` on `colab new`, `colab exec`, `colab upload`, `colab download` and `colab stop` (`--gpu` accepts `T4`, `L4`, `G4`, `A100`, `H100`; add `--high-mem` where supported; default `colab_first` preference `H100`/`G4`/`A100`/`L4` by VRAM need and account entitlement). Check account compute-unit balance with `colab usage` before large batches.
- **Execution & shell commands:** Prefer `colab exec -s <name> -f <script.py|notebook.ipynb>` (reads local files transparently without pre-uploading; kernel state persists across calls in `/content`). For single self-contained jobs, prefer `colab run --gpu <GPU> [--high-mem] <script.py> [args...]` or `scripts/colab_cli.py run-ephemeral` so teardown happens automatically even on script error. For one-shot shell commands, run `colab ssh -s <name> -- <cmd>` (redirect stdin `</dev/null` in agent shells and pass untrusted arguments as separate argv tokens after `--`); if local `ssh`/key is unavailable or concurrent SSH returns HTTP 429, fall back to `colab exec -s <name>` with `%%bash` or Python `subprocess.run` + `--env`.
- **Minimal transfer & Blender Cycles GPU parity:** Transfer only the active shot's required payload (conditioning image, control clip, or self-contained packed `.blend`). For headless Blender Cycles offloads (`scripts/colab_cli.py blender-render`), keep raw PNG sequences on `/content`, select `OPTIX` on hardware ray-tracing GPUs (`G4`/`L4`) and explicitly select `CUDA` (with GPU OpenImageDenoise when supported) on non-RT datacenter GPUs (`A100` SM80, `H100`, `T4`) where first-time OptiX kernel compilation can stall, encode the Rec.709 CFR MP4 on the VM, and download only that encoded clip plus its metadata/receipt—never whole raw PNG frame directories over the wire. Verify downloaded media locally with `ffprobe` and normal-speed viewing.
- **Mandatory teardown & recovery:** Idle Colab VMs continuously burn compute units. Always terminate newly allocated runtimes with `colab stop -s <name>` as soon as outputs are downloaded and hash-verified (or rely on `colab run` / `scripts/colab_cli.py` `finally:` teardown). Use `colab restart-kernel -s <name>` to recover a wedged kernel before reprovisioning; on backend eviction (`404`/`401`), reconcile active runtimes with `colab sessions` and check saved local/Drive outputs before resubmitting. Bind `tool_applications` (`source_id: "google-colab-cli"`, `usage_mode: "runtime"`) or `run.json` `compute_node` evidence honestly; remote execution completion (`complete_unreviewed`) is never scientific, motion or audiovisual acceptance.
